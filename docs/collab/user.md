# 회원정보·개인정보 보유·탈퇴·파기 정책

## 1. 기본 원칙

한글과 세종의 회원정보 및 개인정보는 다음 원칙에 따라 관리한다.

1. 회원 계정의 이용 여부와 신청·결제·상담 등 업무 개인정보의 보존 여부를 분리하여 관리한다.
2. 회원 탈퇴가 이루어졌다고 해서 신청·결제·문의 등 별도의 보존 목적이 있는 업무 데이터를 일괄 삭제하지 않는다.
3. 각 개인정보는 개인정보처리방침에 정한 처리 목적 및 보유기간까지만 보관한다.
4. 보유기간이 끝나거나 처리 목적이 달성되어 더 이상 필요하지 않은 개인정보는 파기한다.
5. 다른 법령에 따라 일정 기간 보존해야 하는 기록이 있는 경우에는 해당 법정 기간 동안 별도로 보존한 뒤 파기한다.
6. 회원 계정 삭제와 업무 데이터 파기는 각각 독립적인 정책과 시점에 따라 수행한다.

### 1.1 개인정보처리방침 고지 보유기간 표 (2026-08-19 확인)

현재 개인정보처리방침 문서에 실제로 고지된 항목별 보유기간이다. 회원 탈퇴(계정 즉시 삭제, §2)와는 **별개의 독립적인 상한선**이다 — 탈퇴하지 않아도 아래 기간이 지나면 해당 개인정보는 파기 대상이 되고(§15 파기 배치, 아직 미구현), 탈퇴하면 그보다 먼저 계정이 즉시 삭제된다. 두 트리거 중 먼저 도래하는 쪽이 적용된다.

| 개인정보 유형 | 보유기간 | 해당 데이터 |
|---|---|---|
| 본인확인용 일부 정보 | 본인 확인 후 즉시 파기 | §6 참고 |
| 상품 제작 신청정보 | 상품 수령 후 6개월 | `Application`/`Applicant`/`ApplicationMember`/`Receiver`, §5 |
| 결제정보 | 상품 수령 후 6개월 | 결제·거래 기록, §7 |
| 고객상담 정보 | 상담일(문의 접수일)로부터 6개월 | `Inquiry`, §8, `docs/specs/inquiry/requirements.md` §⑧ |
| 홈페이지 회원가입 정보 | 문서상 "상품 수령 후 6개월" | `User`(name/email/phone/passwordHash 등) — ⚠️ 아래 §17.1 참고 |

✅ **"홈페이지 회원가입 정보"의 보유기간 — 2026-08-19 해소(§17.1 참고)**: 문서상 "상품 수령 후 6개월"이 맞다(오탈자 아님). "상품 수령 후 6개월"은 **탈퇴하지 않고 계속 활동하는 회원**에게 적용되는 기본 보유기간(만료 시 파기 대상)이고, **회원탈퇴 시에는 이 기간을 기다리지 않고 지체 없이 파기한다** — 탈퇴/보유기간만료 중 먼저 도래하는 사유로 파기된다는 뜻이다. 즉 이번에 확정한 "탈퇴 시 즉시 `User` 하드 삭제" 정책은 이 보유기간 상한선보다 항상 먼저 적용되는 별도 트리거이며, 두 규정은 서로 모순 없이 병행한다.

# 2. 회원 계정 정책

## 2.1 회원 탈퇴

회원 탈퇴는 요청 즉시 확정한다.

기존의 다음 정책은 폐지한다.

* 탈퇴 후 7일 복구 유예기간
* 탈퇴 후 로그인 시 자동 복구
* OAuth 로그인 시 자동 복구
* `User.isRestorable()`
* `User.restore()`
* 7일 경과 후 User 익명화
* 회원 복구를 위한 `withdrawalRequestedAt` 기반 상태 관리

즉 다음과 같이 동작한다.

```text
ACTIVE 회원
    ↓
회원탈퇴 요청
    ↓
본인 확인 및 탈퇴 검증
    ↓
모든 로그인 세션 무효화
    ↓
회원탈퇴 즉시 확정
    ↓
User 계정 삭제
    ↓
복구 불가
```

탈퇴한 회원은 기존 계정으로 다시 로그인하거나 계정을 복구할 수 없다.

---

## 2.2 탈퇴 시 User 처리

회원탈퇴 완료 시 `User` row는 물리 삭제(Hard Delete)한다.

삭제 대상에는 User에 저장된 계정·인증용 개인정보가 포함된다.

예:

* 이메일
* 이름
* 비밀번호 해시
* OAuth 식별자
* 휴대전화번호
* 주소
* 기타 계정 프로필 정보

`User`를 신청·결제·문의 이력을 보존하기 위한 목적으로 계속 유지하지 않는다.

신청·결제·문의 등에 필요한 개인정보는 각 업무 도메인이 별도로 보유한 스냅샷 데이터를 이용한다.

---

# 3. 인증정보 삭제 정책

회원탈퇴 시 인증정보는 즉시 사용할 수 없도록 한다.

## Access Token

현재 발급된 Access Token은 즉시 무효화한다.

기존 토큰 블랙리스트 또는 사용자 세션 무효화 방식을 유지한다.

## Refresh Token

탈퇴 회원의 `RefreshTokenSession`은 단순 `revoke` 상태로 남기지 않고 실제 삭제한다.

```text
회원탈퇴
→ Access Token 무효화
→ 해당 User의 모든 RefreshTokenSession 삭제
→ User 삭제
```

탈퇴 이후 인증에 사용할 수 있는 토큰 문자열을 불필요하게 계속 보관하지 않는다.

---

# 4. 동일 이메일 재가입 정책

회원탈퇴 이후 동일 이메일을 사용한 신규 회원가입은 허용한다.

다만 이는 기존 계정의 복구가 아니라 완전히 새로운 회원가입이다.

예:

```text
기존 계정
User #15
email = user@example.com

↓ 탈퇴

User #15 삭제

↓ 동일 이메일 재가입

User #93
email = user@example.com
```

따라서 신규 User는 기존 User와 별개의 계정이다.

기존 계정의 다음 데이터 소유권은 신규 계정으로 자동 이전하지 않는다.

* 신청 내역
* 문의 내역
* 후기
* 기타 `userId`를 기준으로 소유권을 관리하는 데이터

동일 이메일이라는 이유만으로 과거 데이터를 신규 계정에 다시 연결하지 않는다.

---

# 5. 상품 제작 신청 개인정보

상품 제작 신청 과정에서 수집하는 개인정보는 회원 계정과 별개로 관리한다.

현재 개인정보처리방침 기준 주요 수집항목:

* 이름
* 생년월일
* 휴대전화번호
* 이메일
* 주소
* 서명
* 상품 제작에 필요한 신청 정보

현재 고지된 보유기간:

**상품 수령 후 6개월**

따라서 회원이 중간에 탈퇴하더라도 다음과 같은 업무 데이터는 즉시 삭제하지 않는다.

* `Application`
* `Applicant`
* `ApplicationMember`
* `Receiver`
* 제작 및 배송에 필요한 관련 업무정보

예:

```text
상품 수령
2026-08-01

회원 탈퇴
2026-08-10

↓

User는 탈퇴 정책에 따라 삭제

Application / Applicant 등
→ 즉시 삭제하지 않음
→ 상품 수령일을 기준으로 보유기간 관리
```

회원탈퇴와 신청정보 파기는 별개의 사건으로 취급한다.

---

# 6. 본인인증 정보

본인 확인만을 목적으로 수집한 개인정보는 본인 확인이 끝난 이후 계속 보유하지 않는 것을 원칙으로 한다.

개인정보처리방침에 본인확인 후 즉시 파기로 정해진 정보는 인증 결과 확인 후 파기한다.

예:

* 본인인증 과정에서 일시적으로 사용한 정보
* 본인확인 목적의 인증 데이터

단, CI 등 특정 정보를 회원 식별자로 실제 서비스에서 계속 사용할 필요가 있다면 현재 개인정보처리방침과 구현 목적이 일치하는지 별도 검토해야 한다.

---

# 7. 결제 개인정보

현재 개인정보처리방침에는 무통장입금 관련 개인정보를 다음과 같이 규정하고 있다.

수집항목 예:

* 상품 종류
* 금액
* 이체일자
* 계좌번호
* 예금주
* 예금주 생년월일
* 기타 입금 확인 정보

현재 고지된 자체 보유기간:

**상품 수령 후 6개월**

회원탈퇴 여부와 관계없이 결제·거래 기록은 해당 기록의 별도 보존정책에 따라 관리한다.

단, 실제 서비스가 「전자상거래 등에서의 소비자보호에 관한 법률」의 적용을 받는 경우에는 계약·대금결제·재화 공급 등의 거래기록에 더 긴 법정 보존기간이 적용될 수 있으므로, 실제 적용 여부를 확인한 후 개인정보처리방침과 시스템 보존기간을 확정한다.

따라서 현재 개발 정책은 다음과 같이 둔다.

> 결제·거래 개인정보는 개인정보처리방침에 정한 기간과 관련 법령상 의무 보존기간을 확인하여, 실제 적용되는 보존기간 동안 별도 관리한 뒤 파기한다.

최종 법정 보존기간이 확정되기 전까지 결제 데이터를 단순히 6개월 후 자동 삭제하는 스케줄러는 구현하지 않는다.

# 8. 1:1 문의 개인정보

문의 작성 시 다음 개인정보를 문의 건별 스냅샷으로 저장한다.

* `userId` — 소유권 판별
* `name` — 문의 건의 연락자 이름
* `email` — 답변받을 이메일
* `phone` — 연락처
* 문의 내용 및 상담 이력

`name`, `email`, `phone`은 User 계정정보의 단순 참조값이 아니라 문의 접수 당시의 연락처 정보로 저장한다.

현재 보유정책:

**문의 접수일(`createdAt`)로부터 6개월**

회원이 문의 등록 후 탈퇴하더라도 Inquiry는 즉시 삭제하지 않는다.

```text
문의 등록
 ↓
회원탈퇴
 ↓
User 삭제
 ↓
Inquiry 유지
 ↓
관리자 답변 가능
 ↓
Inquiry.email로 답변 알림 가능
 ↓
보유기간 종료
 ↓
Inquiry 개인정보 파기
```

탈퇴 회원이 동일 이메일로 다시 가입해도 과거 Inquiry의 `userId`를 새로운 User의 ID로 변경하지 않는다.

따라서 과거 문의는 신규 계정의 마이페이지에 자동으로 나타나지 않는다.

# 9. 법정대리인 개인정보

만 14세 미만 아동과 관련하여 법정대리인의 개인정보를 수집하는 경우 현재 개인정보처리방침의 기준을 적용한다.

### 동의가 정상적으로 확인된 경우

법정대리인의 동의정보는 해당 아동 개인정보의 파기 시점까지 보관한다.

### 동의를 거부했거나 동의 의사가 확인되지 않은 경우

해당 정보는 **5일 이내 파기**한다.

법정대리인의 개인정보도 User 탈퇴 여부만을 기준으로 일괄 삭제하지 않고, 해당 아동 정보의 보유·파기 정책과 연결해서 관리한다.

# 10. Review 정책

Review는 신청·결제와 같은 법정 업무기록과 성격이 다르므로 회원탈퇴 정책을 별도로 적용한다.

권장 정책:

* 회원탈퇴 때문에 Review 본문을 자동 삭제하지 않는다.
* 작성자의 User 계정은 삭제한다.
* 후기 작성자 표시가 개인정보에 해당하는 경우 탈퇴 이후 표시명을 익명화할 수 있다.
* `Review.userId`는 과거 작성자 식별값으로 유지할 수 있다.
* 동일 이메일로 재가입해도 기존 Review의 소유권은 신규 User에게 이전하지 않는다.

Review의 최종 삭제·익명화 정책은 콘텐츠 운영정책으로 별도 확정한다.

---

# 11. Board 및 관리자 감사로그

회원 또는 관리자 User가 삭제되더라도 과거 업무이력 자체를 함께 삭제하지 않는다.

대상 예:

* `Board.createdByUserId`
* `AdminActivityLog.adminId`

관리자 감사로그는 다음 목적을 가진 별도 업무기록으로 취급한다.

* 누가 관리자 작업을 수행했는지 확인
* 결제 확인 및 상태 변경 이력 확인
* 운영상 문제 발생 시 추적

따라서 관리자 계정이 삭제되더라도 기존 감사로그의 `adminId` 값을 임의로 변경하거나 감사로그 자체를 같이 삭제하지 않는다.

단, 감사로그에서 관리자 이름·이메일 등 별도 개인정보를 저장한다면 해당 개인정보의 보존기간은 별도로 정의해야 한다.

---

# 12. ApplicationDailyLimit

`ApplicationDailyLimit`은 업무 이력 또는 거래 증빙이 아니라 일일 신청 제한을 위한 운영 데이터이므로 회원탈퇴 시 삭제한다.

```text
User 삭제
→ 해당 User의 ApplicationDailyLimit 삭제
```

동일 이메일로 재가입한 신규 User는 새로운 일일 제한 카운터를 사용한다.

# 13. 데이터별 회원탈퇴 처리 요약

| 데이터                     | 회원탈퇴 시         | 이후 처리           |
| ----------------------- | -------------- | --------------- |
| `User`                  | 즉시 Hard Delete | 복구 없음           |
| Access Token            | 즉시 무효화         | 재사용 불가          |
| `RefreshTokenSession`   | 즉시 Hard Delete | 보존하지 않음         |
| `ApplicationDailyLimit` | 삭제             | 신규 가입 시 새로 생성   |
| `Application`           | 유지             | 별도 보유기간 후 파기    |
| `Applicant`             | 유지             | 신청 개인정보 보유기간 적용 |
| `ApplicationMember`     | 유지             | 신청 개인정보 보유기간 적용 |
| `Receiver`              | 유지             | 신청 개인정보 보유기간 적용 |
| 결제·거래 기록                | 유지             | 법정·정책 보유기간 후 파기 |
| `Inquiry`               | 유지             | 문의 접수 후 6개월 기준  |
| `Review`                | 유지 권장          | 작성자 익명화 정책 별도   |
| `Board`                 | 유지             | 업무 콘텐츠 유지       |
| `AdminActivityLog`      | 유지             | 감사로그 정책 적용      |

# 14. 소프트 삭제 정책 폐기

기존 회원 소프트 삭제 구조는 폐기한다.

제거 대상:

* 탈퇴 후 7일 유예기간
* 자동 계정 복구
* OAuth 자동 계정 복구
* `User.isRestorable()`
* `User.restore()`
* `User.anonymize()`
* 회원 복구 전용 로그인 분기
* 회원 익명화용 `UserWithdrawalScheduler`
* `withdrawalRequestedAt` 기반 복구 판정
* `anonymizedAt` 기반 계정 복구 판정

기존 `UserWithdrawalScheduler`를 단순히 "7일 후 Hard Delete" 스케줄러로 변경하지 않는다.

탈퇴는 즉시 확정되므로 User 삭제 역시 탈퇴 처리 과정에서 수행하는 것을 기본으로 한다.

신청·결제·문의 등 보유기간 만료 데이터를 파기하는 배치 작업은 **회원탈퇴 스케줄러와 완전히 별개의 개인정보 파기 인프라**로 설계한다.

# 15. 개인정보 파기 배치

향후 개인정보 파기 배치는 데이터 종류별 보유기간을 기준으로 처리한다.

예:

```text
Inquiry
createdAt + 6개월
→ 파기 대상

Application 관련 개인정보
상품 수령일 + 확정된 보유기간
→ 파기 대상

결제 기록
관련 법령 및 개인정보처리방침에 따른 기간
→ 파기 대상
```

법령상 보존해야 하는 개인정보가 있는 경우에는 일반 서비스 데이터와 분리하여 저장·관리하고, 법정 보존기간 종료 후 파기하는 구조를 사용한다.

파기 시에는 복구 또는 재생이 어렵도록 실제 삭제한다.

필요한 경우 다음 정도의 파기 감사정보만 별도로 남길 수 있다.

* 파기 대상 유형
* 파기 건수
* 파기 일시
* 파기 작업 결과

파기된 개인정보 원문 자체를 파기 로그에 다시 저장해서는 안 된다.

# 16. 개인정보처리방침과 코드의 우선순위

개발자가 임의로 개인정보 보유기간을 변경하지 않는다.

다음 사항은 개인정보처리방침 또는 관련 법령의 변경과 함께 수정한다.

* 개인정보 수집항목
* 수집 목적
* 보유기간
* 회원탈퇴 후 처리방식
* 법정 보존 대상
* 제3자 제공항목
* 위탁항목

정책 문서와 실제 코드가 다르면 먼저 정책 충돌을 보고하고 임의 구현하지 않는다.

# 17. 현재 개인정보처리방침에서 별도 확인이 필요한 사항

현재 전달받은 개인정보처리방침에는 개발 전 최종 확인이 필요한 부분이 있다.

## 17.1 회원가입 정보의 보유기간 — ✅ 2026-08-19 해소

회원가입 정보에 대해 `"상품 수령 후 6개월"`이라고 되어 있다(§1.1 표에서 문구 재확인 완료 — 오탈자·오독 아님).

**확정 답**: 상품 수령 후 6개월은 **탈퇴하지 않고 계속 활동하는 회원**에게 적용되는 기본 보유기간(=이 기간이 지나면 파기 대상)이다. **회원탈퇴 시에는 이 6개월을 기다리지 않고 지체 없이 파기한다** — 즉 "탈퇴"와 "보유기간 만료" 중 먼저 도래하는 사유로 파기되며, 탈퇴가 발생하면 그 즉시(§2 정책대로 `User` 하드 삭제) 처리되고 6개월 타이머는 애초에 의미가 없어진다. 상품을 한 번도 신청/수령하지 않은 회원은 이 6개월 타이머 자체가 시작되지 않을 뿐이며(기준일 없음 = 파기 트리거가 없을 뿐 문제가 아님), 탈퇴하면 언제든 즉시 파기라는 원칙은 동일하게 적용된다.

## 17.2 비밀번호의 제3자 제공

현재 제3자 제공 항목에 `비밀번호`가 포함되어 있다.

서비스에서는 비밀번호 원문을 보관하지 않고 해시값만 저장해야 하며, 제작업체가 회원의 로그인 비밀번호를 제공받아야 할 정상적인 업무 목적도 확인되지 않았다.

따라서 실제 서비스 구현에서 비밀번호를 외부 업체에 제공하지 않는다.

개인정보처리방침의 해당 항목은 삭제 또는 정정 여부를 반드시 확인한다.

## 17.3 제3자 제공과 처리위탁의 구분

현재 문서의 제2조는 제목은 `"개인정보의 제3자 제공"`이지만 내용 일부는 `"개인정보 처리업무를 위탁"`한다고 작성되어 있다.

제3자 제공과 처리위탁은 법적으로 동일한 개념이 아니므로 실제 제작업체와의 관계가 어느 쪽인지 확인하여 개인정보처리방침 구조를 정리해야 한다.

## 17.4 거래정보 6개월 보관

현재 방침은 일부 상품·결제정보를 상품 수령 후 6개월 보관한다고 규정한다.

실제 한글과 세종의 사업 구조에 전자상거래 관련 법정 거래기록 보존의무가 적용되는 경우에는 이보다 긴 기간 동안 일부 기록을 보존해야 할 수 있다.

따라서 이 항목은 법무·개인정보 담당자 확인 후 최종 확정한다.

# 18. 최종 회원탈퇴 정책 요약

```text
회원탈퇴 요청
        ↓
탈퇴 즉시 확정
        ↓
기존 세션·토큰 무효화
        ↓
RefreshTokenSession 삭제
ApplicationDailyLimit 삭제
        ↓
User Hard Delete
        ↓
복구 불가
        ↓
동일 이메일 신규 가입 가능
        ↓
과거 계정의 데이터 소유권 자동 승계 없음
```

동시에:

```text
Application / 결제 / Inquiry / 감사기록
        ↓
User 탈퇴와 별도로 유지
        ↓
각각의 처리 목적·개인정보처리방침·법정 보존기간 적용
        ↓
보유기간 종료
        ↓
개인정보 파기
```

따라서 이 프로젝트에서 **회원탈퇴 정책과 개인정보 보존 정책은 하나의 삭제 시점으로 묶지 않는다.**

`User`는 계정 데이터이고, `Application`·결제·`Inquiry` 등은 각자의 업무 목적에 따라 별도의 생명주기를 가진다.
